# Plan: user-lines → rows library, replacing the spike-gold system

Status: LANDED (2026-09-19) — the library, the fixtures, and the removals
are on `main`; the snag settle ran as the spike-mapping commits (the six
adjudicated corrections); `make test` is green with no known-red (the 4
pre-existing spike-gold failures are gone), and
`test_the_adjudicated_rows_are_reproduced` pins `rows.json`. One
verification bullet below stays open: "no `spike`/`gold` naming in the
product path" still trips on the VLM-segmentation spike's modules in
`tools/` (`spike_vlm_contract.py`, `word_numbering.py` — see
`vlm-word-segmentation-spike.md`).

## Why

The spike's annotation system (`tools/spike_gold.py`, `test_spike_gold.py`,
`research/spike-word-segmentation/gold/*`) has been failing (4 pre-existing
failures). Root causes, measured:

1. Commit `b844e67` ("bare user-facing line numbers everywhere") removed the
   type prefixes from the identifier format (`seg-1`/`line-41`/`int-41` →
   `1`..`43`) — ids are the same strings in the JSON files and on the
   renders. The committed `gold.json` snapshot was never regenerated to the
   bare scheme.
2. The reconstruction (`build_gold`) disagrees with the user's adjudicated
   mapping on ~40 words (60/70 unplaced; 259, 291, 292, 299–301 placed in
   different labels; the bottom renumbered 37→41, 40→38, 42→38). The word
   data (`words.json`, 455 boxes) and user-line data (`strokes.json`) are
   committed once and unchanged.

User decisions (2026-09-18):

1. **Types return to the file format** — identifiers carry their kind again.
2. **A proper library** for user-provided lines → word boxes, residing with
   the shape-wrangling code in `tools/`, well-named (not "gold"/"spike"),
   unit-tested (all tests pass) plus an integration check against the
   adjudicated row data.
3. **The row data's home** — word data, user-line data, and the adjudicated
   rows live where a fresh agent with no context sees "this is page-01's row
   truth".
4. **After 1–3**, the user answers the snag questions (the snag show below); the rows data is then final.

## Design

### The library (decisions 1, 2, 4, 7) — `tools/rows.py`, class `Rows`

The class lives in `tools/rows.py` (a class's file is named after the
class, per the coding standards). It turns the page's words and the
user's drawn row indications into rows of word boxes:

- `Rows.build(words, user_lines, page_size) -> list[Row]` — present-tense
  verb: builds the rows. One row per user line; a word box goes to the
  first line in reading order that covers its centre (the rule ported
  from the spike extractor, kept faithful — its disagreements with the
  adjudicated data are the snags, never silently "fixed").
- `Row` — the domain record: `id` (typed, stable: `seg-6`, `int-41` —
  the type prefix is part of the file format, restored per decision 1),
  `kind` (`body` | `interjection`), `number` (the user-facing line
  number: `6`, `41`), `word_boxes` (the bounding boxes of the row's
  words — **boxes, never integer ids, which rot**), and `band` (the
  exact union of the word boxes in y and x, never the user line's own
  span).
- Generic rendering helpers live in the library too (tint a page with a
  row's band union). Per-dataset harnesses (page-01) stay thin scripts
  under `research/`.

The user's line indications are named so nobody can mistake their
origin: `user_lines` — the lines the USER drew on the page to say where
the rows are (the wider-world term for this is the user's line
markings; the code says it plainly, and the fixture file carrying them
is `user-row-adjustments.json`).

### The data home (decision 3) — `tests/fixtures/page01-rows-gold/`

Self-describing, one page's row truth in one place:

- `README.md` — what this is, who drew what, what must reproduce it.
- `words.json` — page-01's word boxes (455, existing fixture data).
- `user-row-adjustments.json` — the user's drawn row indications (existing
  `strokes.json`, renamed to say what they are).
- `rows.json` — the adjudicated rows with typed ids: every word the
  user placed, in its row, with the row's band. This is the contract
  the library must reproduce; it is never regenerated by the library.

### Tests (decisions 2, 3, 6) — `tests/test_rows.py`, all green

The library's behaviour, tested — not the fixture's inventory (the
fixture is committed data, and no test re-checks that it contains what
it already contains):

- **The row set**: `Rows.build` on page-01's fixture produces exactly 40
  rows — 37 body rows numbered 1..37 in the reading order of their
  first word, plus the three interjection rows 41, 42, 43 whose words
  are the adjudicated bottom set.
- **One row per user line**: a word appears in exactly one row; the
  bottom's two stroke-passes (38+39, 40+43) are one row each.
- **Bands hug the words**: every row's band is exactly its words'
  union — never a stroke-span rectangle.
- **Determinism**: two builds give identical rows.
- **Integration**: the library's rows equal the adjudicated `rows.json`
  exactly. This is the commitment of the adjudication.

### Removals

Once green: `tools/spike_gold.py`, `tests/test_spike_gold.py`,
`research/spike-word-segmentation/gold/*`, the Makefile freshness
target, `diagnose_sites.py`, `render_expected_map.py`, and the
`spike_vlm_segments` commands that only served them. The numbered-zoom
renders stay (the session's evidence tooling).

### The snag show (decision 4)

After 1–3 are green: one diff, each row = a word whose adjudicated row
differs from the library's placement — word, its box, the adjudicated
row, the library's row — rendered on the page where helpful. The user
rules on each; the rows data is then final.
